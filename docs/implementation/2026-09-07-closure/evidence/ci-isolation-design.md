## Conclusion

GR-03 needs a trusted outer supervisor and a real boundary **at every candidate-command invocation**, including the commands executed from inside the protected claims checker. A workflow-only relocation of current steps cannot supply that property while running the current protected checker unchanged. The smallest defensible implementation is a fixed, digest-pinned Docker execution profile controlled by a supervisor outside the candidate container, plus a narrow transport seam in the protected claim and architecture executors. Preserve all policy comparisons and exact base/head selection. Adopt the transport-aware protected implementation explicitly before it can judge a candidate; do not fall back to the head implementation.

This can be implemented and structurally tested locally. It cannot be claimed isolated or closed on the present local evidence: Docker is unavailable and the supplied bwrap probe was denied. An authorized runner with the actual containment capability must supply the causal isolation regression and end-to-end required-check result. Until then, report `BLOCKED_BY_REQUIRED_CAPABILITY`/`NOT_EXECUTED`, keep GR-03 open, and do not fabricate host proof.

## Trust layout

| Component | Authority and readable/writable resources |
|---|---|
| GitHub runner and trusted outer supervisor | Own exact checkouts, approved supervisor/runtime, Docker control, judge private temp/parsed plan, result records, workflow command files, and final verdict. Never execute candidate scripts directly. |
| Protected judge | Runs outside candidate containers with protected base policy and an immutable exact-head snapshot as data; invokes the closed supervisor for candidate code. Its interpreters/dependencies, temp records, and result channels are not candidate mounts. |
| Candidate container | Only its exact-head execution copy, bounded scratch/home/tmp, fixed read-only image tools, and explicitly approved read-only data. No base checkout, judge private state, host runtime directory, runner workspace parent, Docker socket, host PID namespace, workflow command files, or credentials. |
| Final required-check step | Trusted supervisor output plus workflow-owned step outcomes. It does not read a candidate-created sentinel, candidate JSON verdict, candidate artifact result, or raw candidate log as authority. |

Use an immutable exact-head checkout for policy/data reads and a distinct writable execution copy for commands. The head `.git` history required by current ancestry and routing checks must remain available as exact data. Preserve base/head commit IDs and proof objects; do not substitute an archive that loses Git ancestry. Candidate changes to its execution copy cannot alter the snapshot against which policy is checked.

Sequential claim layers currently share workspace effects. Preserve that where required by reusing a bounded candidate work volume for those layers, while creating a fresh container/process namespace per invocation and leaving the parsed original plan outside. Do not read a candidate-mutated feature list to replace that plan. Keep any change to cross-step workspace reuse explicit; fresh worktrees per layer are not automatically equivalent to the current contract. No candidate writer is alive when the supervisor inspects candidate-produced bytes. Such bytes remain untrusted and can never replace the exact-head policy snapshot.

## Fixed container and observed-exit protocol

Add a closed supervisor, for example `scripts/ci-supervise.py` with a checked-in profile manifest, loaded only from the selected protected base implementation. It must not import Python from the candidate tree, run a candidate Dockerfile/entrypoint, accept arbitrary image names, or allow candidate-provided mount/privilege/daemon options. Python uses `-I`; subprocess argv is structured. All executable tool paths come from the trusted runtime/profile.

The profile uses an immutable image digest containing the approved toolchain (Bash, Git, make, Python plus pinned oracle dependencies, Node 22, the root workflow's ShellCheck/k6 versions, and required fixed utilities). Preparation may provision dependencies before any candidate code starts; candidate `npm ci --ignore-scripts` still runs inside the confined execution environment. Supply a prepared cache or explicitly bounded approved dependency-fetch phase. Never run package lifecycle/build scripts on the host. Do not claim offline compatibility for a consumer whose required verification needs external access; report a missing execution capability unless that access is explicitly supported.

Required controls: separate mount/PID/IPC/network namespaces; non-root UID; no added capabilities and `--cap-drop=ALL`; `no-new-privileges`; fixed seccomp policy; read-only root filesystem; no privileged/user-selected devices; no host network or daemon socket; bounded pids, memory, CPU, storage, output, and wall time. Candidate loopback servers remain possible in its private network namespace. Only the work/scratch destinations are writable; their host parents and supervisor records are not. Storage needs an actual quota or bounded tmpfs, not an unbounded host bind mount disguised as isolation. The final fixed profile must be exercised on the real runner rather than merely asserted in YAML.

For each command:

1. Trusted judge creates a request record with run ID/attempt, event, repository, workflow SHA, exact base/head/judge SHA, image/profile digest, command kind, exact argv or shell bytes, feature/layer identity when relevant, cwd, approved environment, limits, and a fresh nonce. It stores this outside the container.
2. Supervisor creates the fixed container using the exact request. Its only executable command is the selected fixed interpreter/tool. Shell layer bytes are delivered as data to Bash with the same intended eval/exit semantics; never interpolate them into the host shell or GitHub expression source. The candidate controls its own command behavior, not the host invocation or wait result.
3. Supervisor records the actual container ID and verified configuration, starts it, and waits via the trusted daemon. Logs are captured separately as bounded bytes. Do not parse exit status from candidate stdout, from a file in its work volume, or from the exit status of a successful `docker wait` client alone: validate the returned container state/exit code, actual start/finish, timeout/cancellation/OOM flags, and exact container identity.
4. Terminate the entire container and ensure descendants cannot survive before starting the next command. A missing start, daemon failure, inspection error, timeout, cancellation, signal, OOM, uncertain stop, truncated required result, or absent observation is non-PASS. A naturally observed exit zero is necessary for a zero-exit command; nonzero may be a legitimate typed matcher result only under the unchanged protected matcher policy.
5. Supervisor retains a typed observation and logs with command/image/base/head/run bindings. It returns only the observed exit and captured data to the trusted judge. The judge performs existing comparisons, match/no-match classification, filters, claim counting, and verdict logic. Only that outer trusted path writes workflow outputs and observed-zero markers.

Do not expose `$GITHUB_OUTPUT`, `$GITHUB_ENV`, `$GITHUB_PATH`, `$GITHUB_STEP_SUMMARY`, `$RUNNER_TEMP`, `ACTIONS_*` credentials, `GITHUB_TOKEN`, or the supervisor's control socket in the candidate environment/mounts. Buffer candidate logs instead of streaming workflow-command syntax into the runner; publish sanitized data/escaped excerpts or a trusted-created artifact. Candidate text such as `::error::`, output-file instructions, or a forged sentinel is never an instruction to the runner.

## Protected execution seam and policy preservation

The minimal code seam replaces only command execution and acquisition of its actual result:

- In `verify-claims.sh`, the protected loop sends the original exact `cmd` bytes and layer ID to the fixed supervisor, then uses its observed return code and captured log. Parsing, duplicate validation, base-layer identity, no-evidence/no-layers behavior, ordering, counts, and final exit mapping remain unchanged.
- In `check-arch.sh`, send legacy shell bytes or exact typed argv to the same fixed boundary. Apply the existing `match_exit`/`no_match_exit`, ordered regex filters, and `expect` comparison **outside** the candidate container. Do not collapse all nonzero match results into failure or interpret missing execution as a legitimate no-match.
- In `run-gates.sh`, ensure candidate `make check-core` in full mode uses the seam. Keep the quick/full registry and installation applicability unchanged. Data-only protected verifier scripts continue outside the container; audit their subprocess calls so none interprets a candidate file or calls candidate-configured executable behavior on the host.
- Direct root pipeline (`make check`, Gherkin verification, dependency install) and template pipeline use the same supervisor. Host linting may safely treat source as data, but a single fixed execution profile makes routing easier to audit. Preserve all root-specific checks; do not silently add kit-only requirements to consumers.

The seam is selected by trusted CI configuration and a fixed protected helper, not a candidate-supplied executable path or callback. Local legacy behavior can remain available outside protected CI; protected CI must explicitly require the isolated mode and fail when it is unavailable. No environment-only claim such as `ISOLATION_VERIFIED=1` is proof that the correct executor ran.

There is no robust minimal way to retain the current direct-eval protected script byte-for-byte and intercept arbitrary candidate execution safely. Overriding `eval` through `BASH_ENV`, executable `PATH` shims, rewriting the script on the fly, or substituting a head-derived parser is an undocumented replacement of the judge runtime. Do not use those shortcuts.

Preserve `.harness/judge-contract.json` v1's policy interfaces if their meaning is unchanged. Add a **separate protected execution contract** declaring the isolated transport version and exact supervisor/profile binding. The workflow requires that contract from the exact base, with no head fallback. The adopted protected bundle must include the transport-aware implementation; the old snapshot is insufficient. A new versioned protected bundle or an explicitly reviewed maintenance adoption can do this. The repo owner controls that adoption. If the proposed execution change also changes command semantics, environment-dependent requirements, gate applicability, workspace persistence, timeout policy, or accepted result states, identify that as a policy choice and obtain the corresponding decision; do not smuggle it into a security fix.

## Workflow outline and required check

Retain workflow name and job/check name **Required quality**, events `pull_request`/`merge_group`, exact SHA selection, concurrency key, `contents:read`, and fail-closed final step. A single trusted runner job with confined candidate children is the smallest layout:

1. Resolve immutable identities and check out exact head/base using existing pinned checkout configuration.
2. Verify base judge contract **and** protected execution contract. Load supervisor from that base only. Provision trusted runtime/parser/image before candidate execution; image acquisition/build never consumes a candidate Dockerfile or script.
3. Create immutable target snapshot, candidate work area, and supervisor-owned receipt area. Run protected live quick gates against the exact target with supervised arbitrary matcher execution.
4. Run root lint/Gherkin and dependency/pipeline requirements, or the template pipeline, through the fixed executor. Preserve each required operation's outcome and observed exit.
5. Run the protected claims checker against the same immutable exact target, with each original layer supervised. Run protected decision verification against the original exact head/base data.
6. In `if: always()`, a trusted aggregator verifies every required operation's bound observation, expected zero/matcher semantics, and step outcome. It writes the final summary and exits nonzero for any missing, skipped, cancelled, unobserved, or non-PASS requirement. Container/job failure cannot be softened through `continue-on-error` or `success || skipped` logic.

Using multiple jobs can additionally protect policy/aggregation from unrelated work, but is not a substitute for supervised command execution. A candidate job that runs arbitrary code with its runner's UID/sudo access can alter its own outputs and runner state. A downstream `needs.candidate.result == 'success'` or uploaded `exit:0` file is not the missing trusted observed-exit receipt. If jobs are split, each producer must itself have the outside-container supervisor, and the final **Required quality** job must authenticate producer run/attempt and exact source/profile bindings. Do not introduce a dynamic matrix derived from unchecked candidate strings as a shortcut.

This correction also assumes the workflow/supervisor selection is protected by the adopted repository controls. A check name alone is not proof that candidate-edited workflow code is authoritative. Preserve existing controls; do not switch to `pull_request_target` plus head execution, weaken branch rules, or claim that filesystem isolation solves workflow-source authorization. If the current repository relies solely on a mutable check name, that is a separate owner-controlled policy question.

## Minimum owner decision, stated concretely

**Recommended choice:** authorize development and subsequent explicit adoption of `.harness/protected-judge/v2` with the existing semantic judge contract retained, plus a new strict `.harness/execution-contract.json` for `isolated-command-v1`. The contract binds a reviewed supervisor SHA-256, one immutable OCI image digest, a fixed mount/environment/resource profile digest, and the required outside-container observed-exit protocol. The root workflow selects **base** `.harness/protected-judge/v2`; the consumer workflow selects its **base** root with the same execution contract. Absent or mismatched execution contract means `ADOPTION_REQUIRED`; `.harness/protected-judge/v1` remains historical and is never edited or used as an unconfined fallback. Approve actual source/image/profile digests only after they exist and have been reviewed; this note supplies none and grants no adoption itself.

The exact seam being authorized is the replacement of claim-layer eval and architecture command subprocess execution with a protected supervisor request/observation. The judge still decides what to execute from the original exact-base/exact-head policy and still decides what its result means. Its protected execution helper requires isolated CI mode and is not selectable by the candidate. The `run-gates.sh` candidate `make check-core` call and direct workflow candidate commands use the same transport.

Retained semantics are: original exact command bytes/argv; Bash evaluation of shell commands; target-relative working directory; existing command order and relevant shared execution-workspace effects; existing claim schema and duplicate/state/budget validation; exclusion of `repair` only from protected layer identity; required evidence/layers; typed matcher match/no-match status values and ordered output filters; existing gate applicability; decision-ledger prefix rules; oracle ancestry/receipt rules; actual command-exit interpretation; missing/cancelled/skipped/nonexecuted means non-PASS; PR/merge-group SHA selection; and required check name **Required quality**.
